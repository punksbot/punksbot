# Orchestrer le cycle de vie Message dans ConversationDO

Le `ConversationDO` reste l’autorité unique pour l’identité, l’ordre, les permissions et le cycle de vie d’un Message. Les commandes publiques `message.edit@1`, `message.retract@1` et `message.restore@1` sont exécutées sous le même verrou durable `pending_message_command` que le post. Elles revalident le Punk et son accès Workspace/Conversation avant toute nouvelle attestation, puis immédiatement avant le commit synchrone. Aucun `await` ne sépare cette dernière vérification de la transaction. Un Bot public est refusé ; le service `crypto-erasure` n’existe que sur le chemin interne du finalizer.

Un edit prépare la version suivante dans le `MessageContentDO`, pose la fence non-GC, puis commit atomiquement état, version, journal attesté, résultat idempotent, outbox ordonnée et ledger de finalisation. Tant que le coffre n’a pas finalisé la version, cette projection et tous les curseurs suivants restent bloqués. L’alarme renouvelle la fence et réconcilie sans replay client. Un second edit du même Message est refusé tant que cette finalisation subsiste.

Une rétraction remplace immédiatement la vue publique par un tombstone borné, vide la recherche et masque body, topic et médias. La grâce est exactement de sept jours. Les compteurs de thread sont décrémentés une seule fois et `lastReplyAt` est recalculé comme le maximum de `createdAt` parmi les réponses encore actives ; les descendants d’un parent rétracté restent des entités indépendantes. Une restauration n’est permise que si l’instant du commit est strictement antérieur à `eraseAfter`. Elle relit la version courante via le coffre uniquement pour recalculer les jetons de recherche opaques, puis jette le plaintext avant la transaction.

L’effacement final n’a aucune route publique. Une ligne de planification lie exactement `{messageId, retractionCommandId, eraseAfter}` afin qu’un ancien timer ne puisse effacer une nouvelle génération après restauration et nouvelle rétraction. À échéance, l’alarme traite un seul Message, acquiert le verrou de commande, revérifie ce triplet, appelle `destroyGeneration`, valide la preuve et atteste l’événement 50204. La décision utilise `proof.destroyedAt`, supprime toutes les versions locales et tout ledger de finalisation devenu terminal, vide recherche et projection de versions, puis conserve seulement le marqueur social d’effacement. Une panne après le tombstone du registre mais avant le marqueur Conversation est réparée par replay autonome ; le tombstone reste autoritaire face au PITR.

Toutes les réponses publiques, y compris les replays d’anciennes commandes, relisent ensuite l’état autoritaire courant. Elles déchiffrent uniquement si le Message est encore actif et si sa version n’a pas changé, puis réautorisent et relisent synchroniquement l’état avant de répondre. Les tombstones exposent seulement `retractionKind`, `retractedAt`, `eraseAfter`, `publicReason` pendant la grâce, puis `erasedAt` après l’effacement ; jamais commandId interne, reasonCode, acteur modérateur, événement Nostr, engagement, clé, référence de ciphertext ou jeton de recherche.
